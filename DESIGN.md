# DESIGN.md

## Objetivo

Este documento define os princípios de UX/UI do produto.

O sistema deve transmitir modernidade, confiança, simplicidade e eficiência, sem parecer um ERP tradicional ou um template genérico de SaaS.

A referência principal é a experiência de aplicativos de banco digital modernos, especialmente na forma como apresentam informações, hierarquia visual, ações e navegação.

A inspiração pode ser resumida como:

> Banco digital moderno + operação automotiva premium.

A referência não deve ser copiada visualmente ou em identidade de marca.

O objetivo é criar uma experiência própria para o universo de lava-rápidos e detalhamento automotivo.

---

## Princípio central

> Simples para quem usa, poderoso para quem administra.

O sistema deve esconder complexidade quando possível.

O usuário deve conseguir realizar suas tarefas principais sem precisar entender como o sistema funciona internamente.

A interface deve priorizar clareza, velocidade e confiança.

---

## Personalidade visual

A interface deve transmitir:

- Modernidade
- Confiança
- Organização
- Velocidade
- Profissionalismo
- Tecnologia
- Simplicidade

A interface não deve transmitir:

- ERP tradicional
- Sistema burocrático
- Excesso de informações
- Template genérico de SaaS
- Interface criada automaticamente por IA
- Complexidade desnecessária

---

## Referência de experiência

A experiência deve buscar características encontradas em aplicativos de banco digital modernos:

- Hierarquia visual forte
- Poucos elementos por tela
- Informações importantes em destaque
- Navegação objetiva
- Ações principais facilmente identificáveis
- Espaços em branco
- Feedback claro
- Linguagem simples
- Sensação de controle
- Confiança nas informações

A inspiração é principalmente comportamental e de experiência.

Não copiar componentes, identidade visual ou layouts de outras empresas.

---

# Responsividade

O produto deve ser pensado como:

> Mobile first, desktop friendly.

A interface deve funcionar muito bem em celulares, tablets e desktops.

Não basta simplesmente diminuir a interface de desktop para telas menores.

Cada contexto deve ter uma experiência adequada ao dispositivo.

---

# Contextos do produto

O produto possui três grandes contextos de uso.

## Gestão

Utilizado principalmente pelo proprietário ou administrador.

Características:

- Maior quantidade de informações
- Visão geral da empresa
- Indicadores
- Financeiro
- Clientes
- Estoque
- Configurações
- Gestão de unidades e funcionários

Desktop possui maior importância neste contexto.

---

## Operação

Utilizado principalmente pelos funcionários do lava-rápido.

Características:

- Mobile first
- Poucos cliques
- Ações rápidas
- Botões fáceis de tocar
- Informações objetivas
- Mudança rápida de status
- Visualização clara dos veículos em atendimento

A operação deve priorizar velocidade.

O funcionário não deve precisar navegar por várias telas para realizar tarefas simples.

---

## Cliente

Utilizado pelo consumidor final.

Características:

- Mobile first
- Interface simples
- Poucas etapas
- Linguagem clara
- Visualização dos próprios veículos
- Agendamento
- Acompanhamento do serviço
- Fidelidade

A experiência do cliente deve parecer um aplicativo moderno, não um sistema administrativo.

---

# Veículo como objeto central

O veículo é um dos principais elementos da experiência.

A jornada deve fazer sentido como:

> Cliente → Veículo → Serviço → Atendimento → Pagamento → Fidelidade

Sempre que possível, o sistema deve manter o veículo como referência contextual.

O usuário não deve precisar repetir informações desnecessariamente.

---

# Dashboard

O dashboard não deve ser uma coleção de gráficos apenas para preencher espaço.

Ele deve funcionar como um resumo vivo da operação.

Deve responder rapidamente perguntas como:

- Como está a operação agora?
- Quantos veículos estão em atendimento?
- Quantos estão aguardando?
- Quanto foi movimentado?
- Existem problemas que precisam de atenção?
- Existem solicitações de funcionários?
- Como está o movimento do período?

Informações importantes devem aparecer primeiro.

Gráficos devem ser utilizados somente quando ajudarem na tomada de decisão.

---

# Cards

Cards devem ser utilizados com moderação.

Não transformar toda informação em um card.

Cards devem existir quando ajudarem a:

- Agrupar informações relacionadas
- Criar hierarquia
- Destacar uma informação importante
- Facilitar uma ação

Evitar interfaces onde cada pequena informação possui um card próprio.

---

# Ações

Cada tela deve possuir uma ação principal claramente identificável.

A ação principal deve ter destaque visual.

Ações secundárias devem possuir menor peso visual.

Evitar múltiplos botões competindo pela atenção.

---

# Operação

A tela de operação deve ser uma das partes mais rápidas do sistema.

O funcionário deve conseguir:

- Identificar veículos
- Assumir atendimento
- Alterar status
- Visualizar serviços
- Adicionar serviços
- Registrar pagamento
- Finalizar atendimento

com o mínimo de interação necessário.

Controles importantes devem possuir tamanho adequado para toque.

A informação mais importante deve ser imediatamente perceptível.

---

# Status do serviço

Os status devem ser visualmente claros:

- Na fila
- Lavando
- Secando
- Finalizado

A interface deve deixar evidente em qual etapa o veículo está.

O status não deve depender apenas de cor.

Sempre que necessário, utilizar texto, ícone ou outro elemento visual complementar.

---

# Agenda

A agenda deve ser visual e fácil de compreender.

Não deve parecer uma tabela administrativa complexa.

O usuário deve conseguir entender rapidamente:

- Horários
- Veículos
- Serviços
- Unidade
- Disponibilidade

A experiência deve priorizar visualização e ação.

---

# Financeiro

O financeiro deve seguir princípios de aplicativos bancários.

Valores importantes devem aparecer de forma clara e destacada.

Exemplo:

> R$ 4.850,00

Informações secundárias devem possuir menor peso visual.

Movimentações devem ser apresentadas de maneira simples.

O usuário deve conseguir compreender rapidamente:

- Quanto entrou
- Quanto saiu
- Quanto movimentou
- Por qual método recebeu
- Qual período está sendo analisado

Evitar excesso de gráficos.

---

# Fidelidade

A fidelidade deve possuir representação visual clara.

O programa possui exatamente:

> 8 selos.

A interface deve permitir que o cliente entenda imediatamente:

- Quantos selos possui
- Quantos faltam
- Qual é a recompensa
- Quando pode resgatar

Quando os 8 selos forem completados, a recompensa deve receber destaque.

A experiência deve ser simples e motivadora, sem parecer um sistema de pontos complexo.

---

# Cliente

A experiência do cliente deve priorizar:

1. Veículos
2. Agendamento
3. Acompanhamento do serviço
4. Pagamento
5. Fidelidade

O cliente deve conseguir entender rapidamente o que está acontecendo com seu veículo.

Quando houver um serviço em andamento, essa informação deve possuir destaque.

---

# Navegação

## Desktop

A navegação principal deve seguir aproximadamente:

- Início
- Operação
- Agenda
- Clientes
- Financeiro
- Fidelidade
- Estoque
- Configurações

A estrutura pode evoluir conforme o produto evoluir, mas deve permanecer objetiva.

---

## Mobile

A navegação inferior deve priorizar as áreas mais utilizadas:

- Início
- Operação
- Agenda
- Clientes
- Mais

As demais funcionalidades podem ficar agrupadas em "Mais".

---

# Feedback

Toda ação importante deve fornecer feedback adequado.

Exemplos:

- Salvamento
- Pagamento
- Alteração de status
- Agendamento
- Cancelamento
- Solicitação de estoque
- Resgate de recompensa

O feedback deve ser:

- Claro
- Rápido
- Contextual
- Discreto

Evitar excesso de notificações e animações.

---

# Estados da interface

Todas as telas importantes devem considerar:

- Estado normal
- Carregamento
- Estado vazio
- Erro
- Sucesso
- Confirmação
- Falta de permissão

Estados vazios devem orientar o usuário sobre o próximo passo.

Exemplo:

> Nenhum veículo cadastrado ainda.

> Cadastre o primeiro veículo para começar.

Sempre que possível, oferecer uma ação contextual.

---

# Erros

Mensagens de erro devem explicar:

1. O que aconteceu
2. O que o usuário pode fazer

Evitar mensagens técnicas para usuários comuns.

Evitar mensagens genéricas como:

> "Ocorreu um erro."

Quando possível, explicar o problema de maneira humana.

---

# Confirmações

Ações destrutivas ou importantes devem solicitar confirmação quando necessário.

A confirmação deve explicar claramente o que acontecerá.

Evitar confirmações desnecessárias para ações simples e reversíveis.

---

# Design Tokens

Os valores abaixo representam a base visual inicial do produto.

Eles devem ser reutilizados antes da criação de novos valores.

## Tipografia

Fonte principal:

> Inter

Pesos:

- 400 — Corpo
- 500 — Labels e informações secundárias
- 600 — Títulos
- 700 — Destaques e números importantes

A hierarquia tipográfica deve ser mais importante do que o uso excessivo de componentes visuais.

---

## Espaçamento

Escala base:

- 4px
- 8px
- 12px
- 16px
- 24px
- 32px
- 48px
- 64px

Priorizar consistência.

Evitar criar valores arbitrários sem necessidade.

---

## Border Radius

Base:

- Pequeno: 8px
- Médio: 12px
- Grande: 16px

Evitar valores superiores a 20px sem uma justificativa clara de design.

A interface não deve parecer excessivamente arredondada.

---

## Botões

Alturas padrão:

- Compacto: 36px
- Padrão: 44px
- Grande: 48px

O tamanho deve considerar principalmente o contexto de uso.

Botões utilizados frequentemente em telas operacionais devem possuir área de toque confortável.

---

## Ícones

Tamanhos principais:

- Pequeno: 16px
- Padrão: 20px
- Grande: 24px

Ícones devem complementar a informação.

Não utilizar ícones apenas para decorar.

---

## Cor principal

Azul petróleo:

> #0F4C5C

Utilizado principalmente para identidade, elementos institucionais e componentes de destaque.

---

## Cor de ação

Azul vibrante:

> #1677FF

Utilizado principalmente para ações primárias e elementos interativos.

---

## Fundo

> #F7F8FA

Utilizado como fundo principal das interfaces administrativas.

---

## Superfície

> #FFFFFF

Utilizado para superfícies, áreas de conteúdo e elementos que precisam de destaque sobre o fundo.

---

## Texto principal

> #17191C

Utilizado para informações principais e títulos.

---

## Texto secundário

> #6B7280

Utilizado para informações auxiliares.

---

## Bordas

> #E5E7EB

Utilizado para separação visual discreta.

---

## Estados

Sucesso:

> #16A34A

Aviso:

> #D97706

Erro:

> #DC2626

As cores de estado não devem ser utilizadas como único meio de comunicação.

---

# Sombras

Sombras devem ser discretas.

Evitar interfaces com sombras pesadas.

A hierarquia deve ser criada principalmente através de:

- Espaçamento
- Tipografia
- Contraste
- Superfícies
- Bordas

---

# Gradientes

Gradientes não fazem parte da linguagem visual principal.

Não utilizar gradientes apenas para criar aparência de modernidade.

---

# Glassmorphism

Não utilizar glassmorphism como padrão visual.

A interface deve ser limpa e funcional.

---

# Badges e Pills

Evitar transformar todos os elementos em badges ou pills.

Utilizar esse padrão somente quando houver uma necessidade real de indicar:

- Status
- Categoria
- Estado
- Informação curta

---

# Ícones e Emojis

Ícones devem ser utilizados de maneira funcional e consistente.

Emojis não devem ser utilizados como elemento principal da interface.

Evitar interfaces carregadas de ícones e emojis.

---

# Componentes

O sistema deve possuir componentes reutilizáveis.

Antes de criar um novo componente ou padrão visual, verificar se já existe uma solução adequada no design system.

Evitar criar múltiplas versões do mesmo componente sem necessidade.

A consistência visual deve ser priorizada.

---

# Regra de reutilização

Antes de criar uma nova solução visual:

1. Procurar componentes existentes.
2. Verificar padrões já utilizados.
3. Reutilizar quando possível.
4. Adaptar apenas quando necessário.
5. Criar um novo padrão somente quando houver uma necessidade real.

O objetivo é evitar crescimento descontrolado do design system.

---

# Acessibilidade

A interface deve considerar:

- Contraste adequado
- Tamanho adequado de texto
- Áreas de toque confortáveis
- Estados visuais claros
- Navegação por teclado quando aplicável
- Não depender exclusivamente de cor
- Mensagens de erro compreensíveis

A acessibilidade deve fazer parte da implementação, não ser adicionada posteriormente.

---

# Responsividade

Os layouts devem se adaptar ao contexto.

Desktop não deve ser simplesmente uma versão ampliada do mobile.

Mobile deve priorizar:

- Ações rápidas
- Conteúdo essencial
- Navegação simples
- Área de toque confortável

Desktop pode utilizar:

- Mais informações simultâneas
- Maior densidade de dados
- Navegação lateral
- Visualizações mais amplas

---

# Princípios para criação de novas telas

Antes de criar uma nova tela, responder:

1. Qual é o objetivo principal desta tela?
2. Quem está utilizando?
3. Qual é a principal ação?
4. Qual informação precisa aparecer primeiro?
5. O usuário consegue entender o que fazer sem explicação?
6. Existe algum componente existente que pode ser reutilizado?
7. A tela funciona bem no celular?
8. A tela está visualmente consistente com o restante do produto?

Se uma tela não conseguir responder claramente essas perguntas, sua estrutura deve ser reconsiderada.

---

# Anti-padrões

Evitar:

- Dashboards cheios de gráficos
- Cards para absolutamente tudo
- Excesso de bordas
- Excesso de sombras
- Gradientes decorativos
- Glassmorphism
- Pills em excesso
- Botões demais
- Ícones decorativos sem função
- Emojis em excesso
- Textos genéricos de SaaS
- Interfaces visualmente carregadas
- Componentes diferentes para a mesma finalidade
- Layouts que parecem gerados automaticamente por IA
- Complexidade visual sem benefício funcional

---

# Direção final

A experiência visual deve transmitir a sensação de:

> "Um banco digital moderno, se ele tivesse sido criado especificamente para operar lava-rápidos."

Essa referência serve para orientar a qualidade da experiência, não para copiar a identidade de qualquer empresa.

O produto deve parecer próprio, profissional e coerente.

A interface deve ser:

> limpa, rápida, moderna, confiável e extremamente fácil de entender.

O sistema deve parecer uma ferramenta profissional criada para uma operação real.

Não deve parecer um protótipo.

Não deve parecer um ERP antigo.

Não deve parecer um template genérico.

E não deve parecer uma interface gerada automaticamente por IA.
